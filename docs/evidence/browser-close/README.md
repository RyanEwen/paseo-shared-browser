# Browser close verification

Close shared browser remained in source but was clipped in the live Actions menu after adding the two-line Print row. A fixed menu-height estimate omitted the new row, and `overflow: hidden` on the ScrollView prevented scrolling. The shared menu now measures rendered content, bounds it to the pane, and preserves scrolling with a visible cue when needed. Close remains the final destructive action. Reconnect viewer retains its connection-recovery purpose and does not restart Chromium.

[Rendered Actions menu](actions-menu.png) shows the production Actions component in tall, short and compact React Native Web panes. Close is immediately visible in the tall and compact panes. [After scrolling](actions-menu-scrolled.png) shows the short pane's final row; native Chromium mouse input successfully activated it. The production tab component's final-tab close button is enabled in the fixture.

Closing the final tab requires a browser-close confirmation explaining the effect on all workspace viewers and agents, loss of unsaved page changes, and retention of saved site data. The confirmed tab, viewer, session, runtime and control basis are pinned. A supervisor check of the exact sole target and the subsequent stop share the workspace operation queue. A changed target set refuses the operation before invalidating viewers; expired control and revoked agent authority are checked again at the stop boundary. Ordinary tab close cannot silently upgrade to browser close.

The agent tool defaults to `scope: "tab"`. Explicit `scope: "last-tab"` stops the final workspace browser and returns `browserClosed: true`, without automatic reopen. Actual target counts include Print preview. Closing a sole content page while previews remain is refused; cancel/close the preview first, then confirm the final-tab browser close. No preview source relation is guessed.

Two real Chromium lifecycle tests passed in disposable containers with explicit isolated binaries and host. The human route used a private headed Xvfb display and also opened a real Print preview, verified source-close refusals with both scopes, cancelled the preview through its close lifecycle, and then closed the final content tab. The agent route exercised the shipped stdio tool in default headless mode. Both tests verified changed-tab-list refusal, ordinary multi-tab close preserving the source draft, exactly one workspace runtime stopping, both attached viewers receiving the closed state, refusal of background reattach, retention of an unrelated workspace's runtime and unsaved draft, and explicit reopen preserving a cookie and localStorage while discarding the stopped page's unsaved draft. A print acknowledgement timeout was handled by observation without repeating Print.

Required frozen dependency installation, check, build, typecheck, 14 script tests and 1,044 unit tests passed. Focused guard coverage includes preview preservation without native close dispatch, queued creation, stale identities, control expiry, and agent revocation during target discovery. The check command reported only existing informational lint notices.

Review found and fixed a pending-state edge when a panel switches workspaces during tab close. The new workspace resets tab-operation state, and each operation retains a unique receipt so a late success, error or finalizer cannot affect a newer operation, including switching away and back. An additional supervisor regression test verifies that a stale-tab attachment arriving during the final-target check cannot create a replacement browser behind the close. Required source checks and suites passed again after this review fix; the existing real Chromium lifecycle and rendered-menu evidence remain applicable to the unchanged native and menu paths.

Rendered proof covers the production menu and tab components in an isolated React Native Web fixture. It does not claim acceptance in the live Paseo host UI or native mobile clients. Runtime proof covers the real policy/supervisor and shipped stdio routes. Production browsers and the shared desktop were not used or changed for this follow-up. Deployment is a separate lifecycle step and is not implied by these checks.
